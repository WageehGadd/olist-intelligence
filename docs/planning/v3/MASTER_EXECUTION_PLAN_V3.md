## 1. Executive overview

Build a small academic demonstration using the Brazilian E-Commerce Public Dataset by Olist. It will combine reproducible data cleaning and exploratory analysis, SQLite business analytics, one scientifically evaluated delivery-delay prediction task, a small MLP comparison on that same task, and one integrated FastAPI application serving Jinja2/Bootstrap pages and prediction endpoints. ## 2. Business problem, objectives, and outcomes

Olist's historical orders support two practical questions: how did orders, product categories, and delivery outcomes perform; and, among historically eligible delivered orders, can information available at order creation help distinguish orders delivered after the promised calendar date? The project is retrospective and educational, not a live operational service.

Objectives: (1) reconcile core business measures without multiplying one-to-many records; (2) document data quality and produce reproducible analytical outputs; (3) define an eligible population and point-in-time-safe delivery label/features; (4) compare Logistic Regression, Random Forest, and a small MLP on one chronological evaluation design; and (5) demonstrate results in one local FastAPI/Jinja2 application.

Success means the code and report reproduce the decisions and counts, disclose the limits of historical snapshots, pass essential tests, run locally from documented setup instructions, and support a short team demonstration. No model score, production readiness, current online availability, or business impact is promised.

## 6. Dataset facts and scientific constraints

T-00 identified nine related CSVs: orders (99,441), order items (112,650), payments (103,886), reviews (99,224 rows; review_id has 814 duplicate excess), products (32,951), sellers (3,095), customers (99,441), geolocation (1,000,163; ZIP prefix is not unique), and category translation (71). Candidate keys and join caveats are detailed in the T-00 audit. In particular, `customer_id` identifies an order-linked customer row; `customer_unique_id` is the cross-order customer key. Olist has one-to-many order items and payments; aggregate each child to order grain before joining or avoid joining it into monetary totals. Geolocation must not be joined on ZIP prefix without deduplicating/aggregating first.

The T-00 delivery audit found 96,470 eligible historical delivered orders with usable actual/estimated dates and valid chronology; 6,534 were late by calendar date (6.77%). This is an audit population count, not a guaranteed output for altered cleaning rules. For the delivery-delay KPI and ML target only, exclude delivered orders with an estimated calendar date before purchase; retain the existing valid-required-timestamp, actual-not-before-purchase, and delivered-order eligibility conditions. Late means normalized actual calendar date strictly later than normalized estimated calendar date, not timestamp lateness or an arbitrary 30-day rule. These delivery exclusions do not automatically apply to revenue/customer commercial KPIs. Document exclusion counts by reason. Prediction point is order creation. Exclude actual outcome/delivery fields, final status, reviews, post-purchase payments, IDs as predictive numeric variables, and future aggregates. T-00 says cart/original-promise/customer-location snapshots are retrospective availability assumptions, not historically proven versions. Record that caveat; do not claim a deployable live predictor. Split whole orders chronologically; fit encoders/imputers/scalers on train only. Report class balance, average precision and precision/recall/F1 (plus ROC-AUC and calibration where feasible); never use the final test interval to choose features, models, thresholds, or hyperparameters. A small MLP is an educational comparator, not presumed superior.

For prediction input, strictly parse `purchase_timestamp` as source-naive `YYYY-MM-DDTHH:MM:SS` and `estimated_delivery_date` as a valid `YYYY-MM-DD`; require the promised calendar date to be on or after the purchase calendar date. Reject malformed/timezone-bearing values and unsupported fields/types with HTTP 422 `INVALID_INPUT`. Historical training/evaluation rows and inference must call the same pure `src/ml/features.py::derive_model_features` function so date parsing, calendar features, lead-day calculation, item sums/count and the fixed feature order are identical. See Shared Contracts for the complete schema and example.

## 7. Architecture and stack

Raw CSVs under ignored `data/raw/`; local generated artifacts under ignored `data/processed/`; SQLite file under ignored `data/local/`; model file under ignored `models/local/`. Tracked code/docs live in `src/`, `templates/`, `static/`, and `tests/`. Hamza owns SQLite ingest/queries; Hasnaa owns pandas cleaning and EDA; Wageeh owns delivery modeling and FastAPI backend/integration; Rana owns Jinja2/Bootstrap/Plotly UI. One process serves pages and JSON. The four HTML paths `/`, `/sales`, `/delivery`, `/predict` are rendered server-side by Wageeh's FastAPI handlers using Jinja2 context. Rana owns templates and browser interactions: Sales period selection fetches the category-value JSON route; Delivery period selection fetches the monthly-delay JSON route; Prediction form submission fetches the JSON prediction route. Initial page data is server-rendered; no frontend framework is added. Use Python compatible with the repository's observed Python 3.10.20 baseline, Pandas, NumPy, SQLite (`sqlite3`), scikit-learn, TensorFlow/Keras only if install/runtime suitability is confirmed before the MLP task, FastAPI, Pydantic, Jinja2, Bootstrap assets, Plotly, and pytest. Pin only dependencies actually selected and tested. No new environment or package installation is authorized by this planning document.
